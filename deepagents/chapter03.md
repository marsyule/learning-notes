## 0. 核心结论

**虚拟文件系统的价值并不只是“让 Agent 写文件”，而是将大量资料、中间产物与模型当前上下文解耦，让 Agent 在需要时再取回信息。**

一句话理解：

> **当前模型上下文是工作台，文件系统是资料柜；Backend 决定资料保存在哪里，权限规则决定哪些操作能做，Sandbox 决定代码能在什么环境里执行。**

我通过讨论形成的补充认识：

1. **能放进上下文 ≠ 值得一直放在上下文里。** 无关信息可能稀释关键信息、增加输入成本，并挤占后续推理空间。
2. **文件存在 ≠ 当前线程可访问 ≠ Agent 会主动使用。** 必须分别检查存储生命周期、访问边界和检索行为。
3. **持久保存 ≠ 可靠记忆。** 重要信息还需要溯源、覆盖检查、冲突核验，以及从临时结果到长期知识的筛选。
4. **文件工具权限 ≠ 代码执行隔离。** 不可信 Python/Shell 代码应该放进受限的 Sandbox，不能依赖虚拟路径限制保证安全。

## 1. 为什么大上下文窗口仍然需要文件系统？

假设一个科研 Agent 搜索得到 50,000 tokens 的结果，而模型支持 128K 上下文。虽然可以一次性装下资料，但长程任务不应因此把全部资料持续留在对话中。

| 问题 | 直接塞进对话历史 | 文件化并按需读取 |
| --- | --- | --- |
| **相关性** | 包含大量当前步骤不需要的内容 | 可以按任务选取片段 |
| **上下文预算** | 早期检索占用后续分析、工具结果的空间 | 把大资料移出当前输入 |
| **调用成本** | 多轮可能反复处理相同资料 | 减少不必要的重复输入 |
| **可追溯性** | 依赖冗长历史定位证据 | 用路径、段落及原始来源定位 |
| **长期管理** | 中间产物难以分类与复用 | 便于整理、分层、版本化 |

**注意两种风险：**

- **上下文腐蚀**：大量无关或互相干扰的信息进入输入，可能降低模型实际利用关键信息的能力。
- **检索遗漏**：资料不在上下文后，Agent 可能不知道应该读取哪一段。因而“外部存储 + 检索”不一定比直接提供全文更好。

这里的关键不是“尽可能少读”，而是**在效率和证据覆盖之间建立可验证的平衡**。

## 2. 内置文件工具：统一操作抽象

Deep Agents 第三章所述 v0.7 版本包含七种主要文件工具：

| 工具 | 职责 | 容易忽视的行为 |
| --- | --- | --- |
| `ls` | 列出目录和文件元信息 | 用于浏览而非全文检索 |
| `read_file` | 按偏移和数量读取 | 文本可分页；多模态还取决于后端及模型能力 |
| `write_file` | 创建或写入文件 | **已有文件会被完整覆盖** |
| `edit_file` | 精确字符串替换 | 更适合局部修改 |
| `delete` | 删除文件或目录 | v0.7 新增；递归删除会扩大影响范围 |
| `glob` | 按路径模式筛选文件 | 例如 `**/*.py` |
| `grep` | 按字面量查找内容 | 可输出命中文件、匹配文本或计数 |

### 2.1 分片读取与上下文扩展

对于文本，可通过偏移量读取需要的行：

~~~python
# 工具调用示意，非独立可运行脚本
read_file("/workspace/report.md", offset=100, limit=50)
~~~

该例从第 101 行读取 50 行。实际用于论文检索时，可以先定位命中片段，再向前、向后扩展读取邻近段落，防止断章取义。

这种“邻近扩展”是基于内置分片读取能力提出的应用策略，而不是一套默认自动执行的智能检索算法。

### 2.2 搜索返回成功，不代表结果完整

课程指出，`glob`、`grep` 可能出现 `truncated=True` 的截断结果。需要进一步缩小搜索范围或分批检索，不能将“工具正常完成”误判为“证据已经找全”。

此外，内置 `grep` 的核心是字面量匹配，不等于向量语义搜索；语义检索、多查询和重排序属于可选的系统扩展。

## 3. Context Engineering：两种不同的自动管理机制

### 3.1 大工具结果自动卸载（Eviction）

当适用的工具**返回结果**超过约 20,000 tokens（按字符数估算，阈值可配置），文件系统中间件会尝试：

1. 将结果完整写入 Backend。
2. 将留在消息中的大段内容替换为**文件路径 + 首尾各五行预览**。
3. Agent 后续可按需读取该路径中的内容。

**边界条件**：这不是对所有工具统一触发。`read_file`、`ls`、`glob`、`grep` 等内置文件工具不走这条通用卸载路径；工具返回结果与工具调用参数也应区分。只有写入 Backend 成功、文件仍可访问，才谈得上后续恢复。

### 3.2 对话历史自动摘要（Summarization）

当上下文达到设定阈值时：

1. 旧消息可以保存到 Backend，以便回查。
2. LLM 为旧消息生成结构化摘要。
3. **本轮模型输入**改为“摘要 + 近期消息”。

在模型 profile 提供窗口大小的情况下，课程描述的默认触发比例约为上下文窗口的 **85%**；缺少 profile 信息时使用其他固定阈值或自定义配置。

**特别重要的区别**：正常摘要不意味着 LangGraph State 中全部原始消息被直接删除；它主要影响**本次送进模型的内容**。至于原始历史能否在进程重启后取回，还取决于 State / Backend 的持久化配置。

### 3.3 三个彼此独立的问题

| 问题 | 示例 |
| --- | --- |
| **存在性（Existence）** | 论文结果是否仍保存在某个 Backend？ |
| **可访问性（Accessibility）** | 新的线程、Agent 或用户是否能够访问它？ |
| **被利用性（Utilization）** | Agent 是否主动读取它，并且正确利用相关证据？ |

前期讨论中，我曾把虚拟文件系统理解成“Agent 的外部环境”。更准确的理解是：**虚拟文件系统是访问抽象，不保证物理数据位于 State 之外。** 尤其 `StateBackend` 的文件就属于 Agent State。

## 4. Backend：相同文件接口，不同生命周期

| Backend | 主要存储位置 | 适合场景 | 必须理解的前提 |
| --- | --- | --- | --- |
| **StateBackend**（默认） | LangGraph 线程 State | 当前任务草稿、中间计划 | 跨调用恢复需要 Checkpointer + 同一 `thread_id`，或显式传回状态；持久化 Checkpointer 也可跨进程恢复 |
| **FilesystemBackend** | 本地磁盘 | 本地开发、论文文件、CI 工作区 | 写入真实文件；`virtual_mode=True` 不等于沙箱 |
| **LocalShellBackend** | 本地文件 + 宿主机 Shell | 可信的本地开发 | Shell 能操作宿主机，不具备沙箱隔离 |
| **StoreBackend** | LangGraph Store | 跨线程研究偏好和长期记忆 | 要用正确的用户 namespace；`InMemoryStore` 不能跨进程重启持久化 |
| **CompositeBackend** | 按路径分发到不同 Backend | 混合临时与持久化资源 | 每个路径的共享边界和持久化语义取决于实际路由 |
| **Sandbox Backend** | 隔离环境，依服务而异 | 运行实验、处理不可信代码 | 具体隔离强度、网络权限及产物持久性取决于配置 |

### 4.1 StateBackend 不是“内存文件系统”的同义词

**误区**：“StateBackend 是易失的，结束会话文件就没了。”

**修正**：`StateBackend` 的文件跟随线程 State；是否跨调用甚至跨进程恢复由 Checkpointer 和状态管理策略决定。

- 无 Checkpointer、未显式传入旧状态：不应假设两次独立 `invoke()` 会自动共享文件。
- 有持久化 Checkpointer，复用 `thread_id`：可以恢复相应线程的 State（前提是检查点未被清理）。
- 即使有 Checkpointer，改用全新的 `thread_id`：**不会自动继承旧线程的 State**。

**Checkpointer 解决状态恢复；StoreBackend 解决跨线程共享**，二者职责不同。

### 4.2 CompositeBackend：统一视图，按路径路由

以科研 Agent 为例，可以按路径组织：

~~~text
/workspace/plan.md         → StateBackend        当前任务计划
/papers/paper_001.pdf      → FilesystemBackend   本地论文材料
/memories/preferences.md   → StoreBackend        跨线程、按用户隔离的长期偏好
~~~

这是一个**扩展设计示意**，具体路由需要自行配置；课程给出的基础例子是默认 StateBackend + `/memories/` 路由到 StoreBackend。

为什么不全部用 FilesystemBackend？

- 临时任务数据与长期知识的生命周期不同。
- 多用户场景中，需要明确按线程、按用户隔离的边界。
- 论文原文、可复现产物、结构化记忆可能需要不同介质与管理策略。
- 统一磁盘目录虽然简单，但并不会自动解决跨用户授权、生命周期和语义检索。

所以 CompositeBackend 的价值不只是“持久化 + 非持久化”，而是**路径对应不同的数据管理策略**。

## 5. 权限、安全与真实执行边界

### 5.1 三种机制不能混为一谈

| 机制 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| **`virtual_mode=True`** | 受管理文件工具的虚拟路径解析与越界校验 | 不提供完整进程级隔离 |
| **FilesystemPermission** | 文件工具读写等操作的允许、拒绝、审批 | 不自动约束 Shell 内部的读写行为 |
| **Sandbox** | 在执行环境层限制代码及进程资源访问 | 不自动保证应用层访问授权或长期记忆正确隔离 |

符号链接是否越界要看真实路径解析与校验，不能认为所有软链接都会绕过路径限制。对于课程所述 `LocalShellBackend`，`root_dir` 仅规定工作目录，并不能限制 Shell 访问工作目录之外的资源。

### 5.2 普通权限：first-match-wins

~~~python
# 规则示意：具体路径和后端需在应用中配置
permissions = [
    FilesystemPermission(
        operations=["write"],
        paths=["/workspace/secrets/**"],
        mode="deny",
    ),
    FilesystemPermission(
        operations=["write"],
        paths=["/workspace/**"],
        mode="allow",
    ),
]
~~~

普通读写权限按顺序匹配，**更具体的拒绝规则应放在更宽泛的允许规则之前**。未匹配规则时默认允许，所以它不是天然的全局写入白名单。

### 5.3 递归删除是一个特殊情况

讨论中考虑了：如果保护 `/workspace/secrets/**`，Agent 却删除父目录 `/workspace`，会怎样？

核对 [v0.7.0 源码中的 `_find_delete_deny_patterns`](https://github.com/langchain-ai/deepagents/blob/deepagents%3D%3D0.7.0/libs/deepagents/deepagents/middleware/filesystem.py#L345-L388) 后确认：

- 内置 `delete` **不只是用普通的 first-match-wins 判断目标路径**。
- 它还检查递归删除目标的子树是否与任何禁止写入的路径模式有重叠。
- 因此即使一个更早的宽泛 `allow` 允许父目录，后续的 `deny` 仍可能阻止整棵目录树被删除。
- 这主要是**规则模式与子树范围的重叠检查**，并非逐文件扫描全部目录后再决定。

**扩展结论**：自己编写 `PolicyWrapper` 时，若仅用 `path.startswith("/workspace/secrets/")` 检查直接操作，可能漏掉对敏感目录本身或其祖先目录的删除。要同时考虑目标路径与操作的**实际影响范围（Effect Scope）**。

但无论内置检查多完善，Shell 和自定义工具仍可能通过其他路径修改文件，因此不能把文件工具策略当成系统安全边界。

## 6. 讨论延伸：如何让科研 Agent 少读、但不漏读？

> **以下是基于课程能力的应用设计，不是 Deep Agents 第三章默认实现的功能。**

### 6.1 多策略检索 + 邻近扩展读取

针对“关键限制藏在论文第 73 段，但检索没有发现”的问题，讨论提出：

1. **多策略召回**：关键词、语义检索、多查询角度联合召回（语义检索需要额外组件）。
2. **上下文扩展**：命中某段后，读取前后段落以保留论证语境。
3. **溯源关联**：记录论文 ID、章节、页码/段落及证据原文位置。
4. **覆盖审查**：不能仅凭搜索结果数量判断调研充分。

### 6.2 信息覆盖不是检索命中率

一些重要信息根本不会被当前检索问题主动查询到。可增加以下“可能遗漏”的观测信号：

| 信号 | 可能提示的问题 | 局限 |
| --- | --- | --- |
| 研究维度覆盖缺口 | 只查性能，没查局限、失败案例或基线公平性 | 需要先明确研究维度 |
| 证据冲突 | 不同论文结论矛盾 | 冲突可能来自设置差异 |
| 关键结论无溯源 | 总结没有原始出处 | 有出处也不等于出处可信 |
| 反复检索无新增信息 | 可能达到局部饱和 | 也可能检索策略陷入盲区 |
| 文件列表/搜索结果截断 | 有些候选根本未被返回 | 需要继续分页或缩小条件 |

这些都是 **Proxy Signals（代理信号）**，不能证明已经找全所有证据。

### 6.3 多 Agent 与决策反馈

对大规模调研，可将任务分给多个子 Agent，再由负责整合与决策的 Agent 追问缺口、发起追加检索。

**但并行 Agent 不会天然消除共同盲点**：如果所有子任务都按同一错误假设检索，最终总结仍可能一致地遗漏关键信息。可以设计不同检索视角和独立的证据审查。

这与课程后续“子 Agent / 任务规划”等章节相关，属于基于第三章文件存储基础的进一步系统设计。

### 6.4 四层证据记忆（个人扩展方案）

~~~text
L3  全局知识：跨论文共识、争议和研究空白
             ↑ ↓
L2  文档摘要：每篇论文的问题、方法、实验、局限
             ↑ ↓
L1  原子证据：可验证的事实、指标、限制及引用
             ↑ ↓
L0  原始资料：全文 PDF、网页、代码、实验日志
~~~

高层摘要用于快速导航；关键结论必须能向下回溯到原始资料。**不能因为上层摘要没有提及某条证据，就判定它不重要**。

示例证据结构：

~~~yaml
claim: "模型 A 在数据集 B 上有提升"
source:
  paper_id: "paper_023"
  section: "Experiments"
  paragraph: 73
evidence_type: "experimental_result"
limitations:
  - "只在单一数据分布下验证"
verification_status: "needs_review"
~~~

这是自主设计的 Schema，**不是内置 Backend 数据格式**。要降低层级摘要的系统性遗漏，可增加随机原文抽查、针对局限性的定向扫描、证据覆盖矩阵与摘要—原文一致性校验。

## 7. 综合设计：安全的多用户长程科研 Agent

本章最终讨论题是：**Sandbox 完成实验后可能被销毁，如何保存重要产物，同时不让不可信代码直接访问用户长期记忆？**

### 7.1 我提出的基本思路

- 由 `CompositeBackend` 为 Agent 提供统一的文件操作视图。
- 中间任务计划与工作状态放在 `StateBackend`。
- 长期记忆放入 `StoreBackend`，并使用按用户隔离的持久化 Store。
- 不可信 Python 实验在 Sandbox 中运行。
- 自动摘要和工具结果卸载控制当前模型上下文。
- 中间研究结果经过整理、确认有长期价值之后，才提升为记忆。

其中“**从临时研究结果筛选并提升到长期记忆**”是这一套设计最重要的原则之一。

### 7.2 完善后的数据流

~~~mermaid
flowchart TD
  U["用户研究任务"] --> A["主 Agent：计划、判断与编排"]
  A --> C["CompositeBackend：按路径路由"]
  C --> S["StateBackend：当前任务草稿"]
  C --> M["StoreBackend：长期记忆"]
  A --> X["受限 Sandbox：运行实验"]
  X --> E["导出结果文件、日志与指标"]
  E --> V{"可信服务校验结果"}
  V -- "不合格" --> R["记录失败或请求重新执行"]
  V -- "合格" --> F["持久化实验产物与溯源"]
  F --> P{"是否值得长期保留？"}
  P -- "暂时不需要" --> S
  P -- "需要" --> M
  M --> A
  S --> A
~~~

**这里有两个细节不可省略：**

1. **Sandbox 产物先导出，才能防止销毁后丢失。** 重要的大文件、数据集、日志或模型权重应进入持久文件/对象存储；不宜一律塞进 StoreBackend 的长期记忆条目。Store 更适合保存摘要、索引、元数据、证据引用和可复用知识。
2. **结果进入记忆必须通过可信边界。** Sandbox 不应拿到长期 Store 的完整凭证；由应用侧负责用户身份校验、文件内容/格式验证、授权和写入。即使结果“有意义”，也可能携带未经验证的结论或恶意内容。

### 7.3 信息生命周期与职责

| 产物 | 推荐处理 | 原因 |
| --- | --- | --- |
| 当前执行计划 | StateBackend | 贴合任务/线程生命周期 |
| 大论文、实验数据与日志 | 持久文件或对象存储 | 保留原始数据，可复现、可追溯 |
| Sandbox 的临时工作文件 | Sandbox 内暂存 | 需要在销毁前导出重要部分 |
| 用户偏好与长期研究知识 | StoreBackend（持久化 + 用户 namespace） | 跨线程复用 |
| 模型当前需要的少量证据 | 按需放入 Context | 控制输入成本、维持相关性 |

### 7.4 进一步的安全边界

- 用户身份必须来自可信认证机制，不能让模型自行指定租户身份来决定访问权限。
- 文件工具权限、持久存储访问控制、Sandbox 的文件挂载/网络/资源限制需要分别设置。
- 对 Sandbox 导出的文本应视为**不可信数据**，不应把其中的指令当作系统命令执行。
- 涉及用户隐私时，关键证据引用也不能绕过跨用户隔离。

## 8. 本章易错点速查

| 容易误解的说法 | 更准确的理解 |
| --- | --- |
| “128K 能装下，就应该全部装下。” | 还要考虑相关性、后续预算和重复调用成本 |
| “文件被存下，Agent 就会用到。” | 存在性、可访问性、被利用性不同 |
| “虚拟文件系统就是外部磁盘。” | 它是抽象接口；StateBackend 的内容存于 State |
| “摘要之后旧对话被彻底删除。” | 正常摘要主要替换本轮模型输入，原始状态和历史可另外保存 |
| “StateBackend 结束会话就必然消失。” | 取决于 Checkpointer、thread_id 与清理策略 |
| “有 Checkpointer 就可以跨线程共享 State。” | Checkpointer 恢复同一线程；新线程不自动继承 |
| “StoreBackend 天然永久保存。” | InMemoryStore 会随进程结束丢数据；持久化需配置 |
| “virtual_mode=True 就是 Sandbox。” | 路径检查与操作系统级隔离不是一回事 |
| “FilesystemPermission 可以限制任意 Shell 代码。” | 它主要约束受管理的文件工具 |
| “delete 一定只检查目标路径。” | v0.7 内置删除还检查受保护子树的重叠范围 |
| “做了多 Agent 和记忆就不会漏证据。” | 仍需覆盖指标、回查和独立验证 |

## 9. 待实践：把理解变成可验证的结论

以下实验是**后续计划**，不是已经执行的结果。

- [ ] **State 生命周期**：分别测试无 Checkpointer、同一 `thread_id` 的持久化 Checkpointer、新 `thread_id` 的文件可见性。
- [ ] **Composite 路由**：设置 `/workspace/` → State，`/memories/` → Store，观察跨线程差异。
- [ ] **工具差异**：验证 `write_file` 覆盖、`edit_file` 局部修改、`read_file` 分片。
- [ ] **删除保护**：在无敏感数据的测试目录中核验父目录递归删除的拒绝行为。
- [ ] **Sandbox 产物**：执行一个小型 Python 实验，先导出结果，再销毁 Sandbox，核验数据仍能恢复。
- [ ] **覆盖实验**：构造一份关键限制位于末尾的长文档，对比全文输入与多策略检索 + 覆盖检查的表现。

建议每项实验记录：**运行版本、配置、输入、预期、实际结果、Trace/日志、结论与局限**。

## 10. 最终总结

这一章我真正理解的不是几个 Backend 的名称，而是一个更一般的架构原则：

> **长程 Agent 的可靠性来自对信息生命周期的主动管理：哪些内容进入当前上下文、哪些内容暂存、哪些内容长期保存、哪些内容允许被执行，以及结论能否回溯到原始证据。**

更具体地说：

1. **Context 是稀缺的推理工作空间，Backend 是承载信息的存储机制。**
2. **StateBackend、StoreBackend、FilesystemBackend 的差异不仅是存储介质，更是线程边界、共享语义与生命周期。**
3. **自动卸载、自动摘要、检索、记忆是不同环节**，不应因为它们都能降低上下文压力而混为一谈。
4. **安全必须按路径、工具、用户身份和执行环境分层设计。**
5. **对科研 Agent 而言，保存信息只是起点**；溯源、覆盖审查、结果验证与记忆筛选，决定了最终研究是否可信。
